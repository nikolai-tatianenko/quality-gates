The 98 uncovered branches (c8 counts one per untaken arm) are spread over 17 packages; the densest files are `cli/src/index.ts` (13), `code-analysis/src/cli.ts` (6), `bridge/src/server.ts` (4), `bridge/src/view.ts` (3), `parsers/src/xml.ts` (5), `cli/src/output.ts` (4), `dashboard/src/server.ts` (4) and `dashboard/cli.ts` (3). Judgement:

- The gap is concentrated in argument parsing and defaulting in entry points (`cli/src/index.ts`, `code-analysis/src/cli.ts`, `dashboard/src/cli.ts`, `bridge/src/serve.ts`), `??` / `?.` fallbacks on optional fields in parsers (`xml.ts`, `gitleaks.ts`, `npm-audit.ts`), and presentation fallbacks (`bridge/src/view.ts`, `output.ts`). These are defensive defaults whose untaken arm has no behavior of its own.
- `code-analysis` has the lowest ratio (48/56, 85.7%) and the only package with a visible risk: its CLI option branches (`cli.ts` lines 14 to 23) are the user-facing surface of `pnpm analyze`, which is a quality gate itself. Worth a focused test of the option errors; not added here because this task is a review and manifest, and no behavior was found wrong.
- Nothing in the uncovered set is an error path that changes a verdict or an exit code, as far as the file list shows; this was judged from the locations and not by reading each of the 98 arms.
- The 95% floor is met everywhere in aggregate (97.8%); per-package floors are not enforced by c8.

## Isolation findings

- Order: no test depends on the order of other tests or files. Files run in parallel and passed together and individually (`fix.test.ts`, `live.test.ts`, `cli.test.ts`, `ink-ui.test.ts`, `export.test.ts`, `sarif.test.ts` each also run alone). The harness `verify-hooks.mjs` states the same for parallel gates and sorts what they append.
- Persistent folders: tests create their state with `mkdtemp` (121 call sites in 47 files, every one under `tmpdir()`). After the full suite and after the coverage run `git status` was clean and no `.qualitygate/` directory existed in the checkout (only the git-ignored `coverage/` and `output/`). References to `.qualitygate.yml` in tests are files inside those temporary projects or string fixtures. `process.cwd()` is used 23 times as the working directory for spawned CLIs and plugins that only read.
- Build output: `tests/*.test.ts` run the sources through `tsx`; with `dist/` deleted, `fix`, `export` and `sarif` tests pass, and the full `pnpm check` runs the tests before `pnpm build`. The gate order in the manifest still builds in the `full` tier before the smoke gates, which do need `dist/`.
- Network: every `fetch`, `listen(0)` and server in the tests is loopback (`127.0.0.1`) on an ephemeral port. `https://example.com` and similar appear only as strings written into configs. No test needs the internet.
- Time: no test freezes or fakes the clock. There are upper-bound wall-clock assertions (`fix.test.ts` under 4 s for a 300 ms timeout, `gates.test.ts` under 10 s for a 400 ms timeout, `desktop-notify.test.ts` under 2 s twice) that prove a gate did not wait for its 5 s / 30 s / 60 s child. They have a 5x to 10x margin and passed in the full parallel run, where the slowest tests were 20x to 70x slower than alone; they are the likeliest source of a flake on a heavily loaded runner. `mcp-lifecycle.test.ts` polls with a 7 s deadline.
- Environment: some tests need POSIX tools (`sleep`, `true`, `script` for the real-terminal SIGINT test) and spawn `tsx`; they are macOS and Linux only.

## Duplication findings

- 24 test files define their own `cli(...)` helper that spawns `tsx` on `packages/cli/src/index.ts` with slightly different signatures (directory first, arguments first, env overrides, `CI` set or unset), and about 16 define their own `project(...)` helper that writes a temporary `.qualitygate.yml`. The bodies are similar, the parameters are not, and some tests rely on the differences (for example `CI: '1'` versus unset for the live view).
- Test titles and assertions are not duplicated across files in a way that is visible from the titles; I did not diff the bodies.

## Improvements made

None to existing tests. Evidence that none is warranted from this review:

- The slowest tests are slow because of parallel `tsx` process start-up, not because of redundant setup; alone they take 0.4 to 13 s, and the suite takes 58 s for 411 tests in 60 files, many spawning CLIs. Switching them to a built `dist/` would change what they verify, and lowering `--test-concurrency` would lengthen the suite.
- Extracting a shared `cli()` / `project()` helper would touch about 40 files with different semantics, for no measured speed gain, which is a risk to the assertions the task forbids weakening.
- Nothing was skipped, deleted or relaxed.

No code or test changed; this report is the deliverable.
